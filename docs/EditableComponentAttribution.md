It contains only a big-endian TIFF IFD0 ExifIFD pointer and the sRGB/width/height tags, with no Orientation tag. It does not strip metadata or change native bytes, pixel expectations or alpha/color equivalence. ## Why these controls

The completed build113 experiment certified all 35 actual small/4K RGBA inputs but did not remedy retained backing. Candidate entry-to-final RSS/footprint grew 517.20/88.22 MiB versus reference 481.73/44.11 MiB. Candidate 2+8 resources added 132.22 MiB RSS and 108.67 MiB volatile resident after warmup. The largest correlated intervals still include history PNG work, restore, pin creation/apply, and fresh render. Object/FD cleanup is distinct from native backing release.

This proposal splits operations while preserving the actual full-size pixels. The earlier source-cache removal, no-cache drawing, allocator relief and 1024-pixel helper-preview experiments are not repeated or claimed as fixes. In particular, the existing helper preview is not a full-size original replacement.

## The five deliberately unequal cells

Each fresh process runs exactly two warmups and eight measured cycles:

1. `raw-draw`: copy three owned raw providers, create original/base/current images, draw each 1:1 and compare full RGBA. This controls provider and validation overhead
2. `png-write`: the same three raw-provider draws/validations, then exact production `CGImage.writePNG(to:)` for all three full-size images. It never reads, hashes or decodes any written output in that process
3. `png-decode-draw`: create three full-size ImageIO images from already retained PNG Data, using the full-decode cache options of `EditableCaptureAssetStore.read`, then actually draw and compare all three. The input source is Data rather than URL specifically to exclude fixture file reads; this does not claim to exercise the complete persistence API
4. `png-decode-owned-draw`: call the identical full-size ImageIO decoder, then convert each decoded image directly with `vImageBuffer_InitWithCGImage` and only `kvImageNoAllocate` into a new, explicitly owned, full-size premultiplied-last, big-endian RGBA8 sRGB buffer. Check the native return code, pointer, width, height and packed row stride. A public CGDataProvider lease owns only that buffer; no CGContext normalization, snapshot, resize, preview, raw-reference copy or production-renderer dependency occurs. Each decoded-image/source reference scope and nested autorelease pool ends before any of the three actual validation draws. The candidate creates three decoded images plus three canonical images, reports six image creations, three PNG decodes, three owned conversions and three full validations per cycle
5. `editable-render-pin`: copy and validate the same three raw providers; restore the prepared payload in an editor, flatten/decorate and compare current; create a pin, load the same in-memory payload, reopen annotations and invoke its native Apply button; compare actual newly applied current; fresh full-stack render/crop/decorate and compare again. All production admission/projection checks remain active

The editable cell applies the **unchanged** document. It has two restores, one native apply callback, one additional fresh render, six full validations, and zero persistence commits per cycle. It does not claim the changed-annotation gesture, history transaction/reopen, injected durable failure, export, screenshot or full end-to-end work. The other cells each have three full validations; raw and write allocate three provider copies, decode creates three ImageIO images, and the owned-decode candidate adds three canonical provider allocations/conversions. Their total memory/time is not an equal-work speed/remedy comparison, and subtracting cells does not prove isolated allocator ownership.

## Owned-decode admission and evidence boundary

The candidate is admitted only by the exact smoke mode `png-decode-owned-draw` with absolute immutable input and certificate paths. Unknown counts, dimensions, deadlines, tolerances, normalization methods or writes paths fail admission. The regular smoke route remains unchanged. Complete-stage checking now requires the new cell, a distinct process identity, the same installed executable, and the same prepared file/manifest/certificate hashes; old four-cell evidence cannot masquerade as a completed five-cell experiment.

Each of the three per-cycle conversion records binds the PNG and raw-reference byte counts and SHA256 values. It records the decoded metadata exactly as certified and the canonical output metadata exactly as raw-draw, including width, height, row stride, bit depth, channel/alpha bitmap description, color-space name/model/ICC, rendering intent and interpolation policy. The report preserves the actual conversion return and flags; the checker requires zero and `kvImageNoAllocate` (512), and a native admission test binds that constant to the SDK. Apple's [vImage conversion contract](https://developer.apple.com/documentation/accelerate/vimagebuffer_initwithcgimage(_:_:_:_:_:)) permits conversion to the supplied format into caller-provided destination storage with this flag. It does not prove the absence of private conversion scratch or framework caching.

For each role, all eight backing counters and full Mach observations are recorded before decode, after decode, after conversion with the decoded image explicitly kept alive, and after its reference/pool scope ends. All three release observations must precede creation completion and the first validation draw. Each draw retains its existing before/draw/compare checkpoints. The checker rejects wrong work counts, wrong or missing conversion records, alternate flags, metadata/hash/extent drift, backwards stage order, missing release-before-draw evidence, incomplete cleanup, and a missing candidate process.

Exact pixels on these three sRGB RGBA8 assets are required but establish only this fixture's fidelity. Display P3/wide-gamut input, grayscale, 16-bit or floating/HDR input, other profiles and alpha edge cases require separate full-size equivalence and bounds tests if eventual production scope expands. Neither this candidate nor existing small previews authorize a full-size original replacement for those formats.

## Allocation baselines, lifecycle and accounting

All consumers retain the same complete PNG/raw/document bytes and the same three explicitly owned validation contexts from a reported preparation baseline. There are no per-cycle snapshots of those destinations. Each fixed destination is cleared, copy-blend drawn 1:1 with no interpolation, flushed, and read in full with `memcmp` and SHA256. A borrowed no-copy Data view hashes bytes without retaining another full raster. All reports retain bounded scalar records only.

Entry is the first fixture boundary after app startup, not process birth. The report separates entry, input load, destination preparation, each cycle's work/draw/compare and release, warmup baseline, measured end, destination release and final input release. The checker independently derives entry→input load/preparation, preparation→warmup, warmup→measured, all eight measured release increments including warmup→measured 1, every subsequent late increment and the final three separately, entry→final, and cleanup changes. It also exposes entry→sampled-peak deltas, per-cycle sampled/checkpoint peaks, native kernel lifetime peaks and the candidate’s per-role decode/conversion/release stage costs. These deltas remain signed and distinct.

Owned raw-provider, candidate normalized-provider and destination allocations have release callbacks and exact active-byte/count checks. Every cycle scopes image references, closes/detaches controllers/windows, drains the autorelease/run-loop boundary, and requires zero retained non-window AppKit/Swift weak probes, zero attached closed-window graphs, zero fixture FDs, zero export jobs/controllers and zero projection reservations. Direct weak CGImage/CGDataProvider/CGContext probes are deliberately absent: a separate build114 test demonstrated an Objective-C weak-registration abort involving CF image/provider probes, without identifying which CF object or proving product over-release. The canonical comparison also avoids the existing reference helper's hidden weak CGContext registration. Newly applied pin pixels are validated, but CF object liveness is not claimed from a weak probe. The candidate’s end of supplied decoded-reference/pool scope is recorded separately from native lifetime: ImageIO and rendered native object/backing lifetime remain unproved. The candidate provider callback releases only its own `OwnedBytes`; ten allocations, ten callbacks, ten deinitializations per role and zero active owned bytes are required after the 2+8 cycles. ImageIO's private provider callbacks are not instrumented; zero owned counters do not prove physical backing release.

All eight counters are preserved: resident size, physical footprint, volatile resident/virtual/pmap, volatile and volatile-compressed ledgers, and compressed bytes. The existing 50 ms sampler records per-phase/all-run observed peaks, minima, field availability and sample counts without retaining unbounded sample arrays. Native boundary records preserve both full Mach flavors and kernel RSS/footprint lifetime peaks. Calls are not atomic; overlapping ledgers are never added as separate causes. Account scope excludes WindowServer/GPU/other processes. `measuredDiskReads=0` means the fixture code does no input/output file-content reads in cycles; it is not system-wide I/O instrumentation.

No global cache, default changes, pressure, purge, allocator relief or helper is used.

## Bounds and running later

Hard limits are fixed in source: 40 MiB per encoded PNG, 210 MiB prepared bundle, 320 MiB aggregate retained writer outputs, 30 output files, 2 MiB per report, 10 cycles per consumer, native 300 seconds and LaunchServices 600 seconds per process. The existing bounded-command wrapper adds a 620-second launcher-process bound and caps each launcher log at 2 MiB; it does not relax native/owned-launcher deadlines. There are now eight sequential process launches (prepare, certify, five consumers, verify-writes). The full wrapper-window sum is 8 × 620 = 4,960 seconds, or 5,000 seconds including every 5-second termination grace; a 4,400-second outer job cannot cover that bound. Opt-in outer integration may use 5,200 seconds with an 88-minute step and 160-minute job to cover bounded waiting, setup and checker margin. This changes only the enclosing orchestration; native 300-second, launcher 600-second, wrapper 620-second and product limits remain unchanged. Failed/malformed/partial evidence fails completion. No environment variable can override dimensions, counts, tolerance or deadlines.
