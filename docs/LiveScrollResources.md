# Continuous-scroll resource qualification

This is a predeclared finite-workload check, authored after the focused build-220 demonstration. No native resource result is claimed by this document. The accepted installer remains build 214 until the current package passes its separate gates.

The tested path is a direct, independently owned pixel source through the production `LiveScrollSessionController`, matching, incremental disk strips, visible growing thumbnail, native Finish button and bounded PNG writer. ScreenCaptureKit acquisition, WindowServer/GPU cost and the AppDelegate history/editor recipient are excluded. The source is explicitly injected; it never grants permissions or reads the desktop.

## Fixed work and process separation

- Two warmup cycles and eight measured cycles in one fresh release application
- Each cycle supplies 218 opaque sRGB BGRA frames of 1280 × 960 pixels at a bounded 15 fps maximum, including a 72-pixel fixed header and 12 reverse observations
- Offsets: 0, then 32 through 3072 in steps of 32, then 3040 down to 2688, then 2720 through 6144, then 6176
- Finish must produce exactly 1280 × 7136 pixels, including the pending final 32-pixel edge
- A separate certification process prepares the immutable raw input and independently verifies native channel conversion and one full output
- The measured process does no reference-image drawing or PNG decoding; a third process checks every pixel of all ten output PNGs against the raw expected bytes

Actual source/strip counts are reported. Arithmetic predictions of 66/67 source records are diagnostics, not correctness criteria. The exact accepted frame count, final dimensions, preview availability and independent output equality are required. The source retains at most the current frame and previous anchor, with provider release accounting; weak session/source/window ownership and exact owned spool removal are checked after closure.

## Time and memory boundaries

Every session retains the existing 180-second product limit. Each fresh application retains the existing 600-second launcher bound; the resource mode has a nominal 590-second cooperative budget. Startup consumes part of that margin. A first-cycle estimate can classify the unchanged ten-cycle workload as incomplete; it cannot reduce the count and call it passed. Outer orchestration permits the four separate demo/certification/measurement/validation launches, while the existing full-job cap remains independent.

The release clock starts when the output is explicitly released and the session helper returns. Both 150 ms and 1000 ms observations are preserved with actual timestamps, before any discretionary drain wait. The report retains absolute entry, cold, warm, late and final readings, sampled peaks and available kernel peaks. RSS, physical footprint and volatile backing are separate accounting views; they are not added together or treated as interchangeable.

Predeclared measured/late gates use the 4,915,200-byte viewport size: growth from cycle 2 to cycle 10 must be no more than two viewports, and each of the final three increments and their sum no more than one viewport. These gates apply separately to RSS, physical footprint and combined volatile ledger observations. Missing observations are incomplete, not zero. Existing 3 GiB RSS and 512 MiB footprint watchdogs remain unchanged.

The initial byte-derived cold targets are **diagnostic estimates only**: 26,607,616 bytes final growth and 129,171,456 bytes sampled peak growth. The report says whether each target was met. A miss is never relabeled a pass; a bounded one-time framework cost requires interpretation, while sustained growth, retained owners or incorrect pixels blocks acceptance. These targets and distinctions are fixed before the first native run.

This finite check does not establish zero leaks, a global memory ceiling, long-duration stability or real desktop capture. Full existing regression, model and installed-package checks remain separate requirements.
