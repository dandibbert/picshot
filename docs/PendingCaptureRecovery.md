# Failed capture completion and pending recovery

A screenshot is not safely handed off merely because `openEditor` was called. It now returns a Boolean: a full six-window limit, exhausted editor admission budget, incompatible active frozen editor, or failed editable restore returns false. All existing editor callbacks (editable history, editable pinning, original/current pinning, save, OCR, translation) remain connected.

The capture completion transaction attempts automatic history and editor admission independently. If either succeeds, that owner keeps the capture. If both fail, one `PendingCaptureRecovery` owns the same selected `CGImage`, original capture date and known encoded backing count. It never keeps `FrozenCapturePresentation`, so the full frozen desktop is released when the acquisition task returns. No recovery thumbnail, export snapshot, provider-data readback, or full-image clone is created.

The compact non-modal panel offers Retry Editing, Save PNG and an explicit, confirmed Discard. Close/Escape hides it; another capture request, Window → Unsaved Capture, or a quit attempt brings it back. A refused retry, cancelled file picker, encoder/write failure, destination collision or cancelled save leaves the original pixels and date intact. Save success means an exclusive PNG publication actually committed. A stale completion cannot resolve another capture. Quit is refused while pending, including rechecking after asynchronous recording termination. Forced process termination/crash/power loss cannot preserve this memory-only fallback when disk writes have failed.

A pending result blocks replacement and all new screenshot/preset/scroll acquisition. One active scroll controller blocks competing screenshot acquisitions until it closes, preventing a late second scroll result from replacing the single recovery slot. Before acquisition, already-full editor count and exhausted retained-byte admission are refused before hiding windows, delays, permission prompts or screenshot APIs. This check does not reserve a speculative maximum screenshot and does not reject ordinary screenshots merely because the maximum possible one would not fit.

## Exact managed-backing limits and remaining resource boundary

The existing editor policy is unchanged: at most **6 editors** and **805,306,368 bytes (768 MiB)** at admission. Existing edits can grow afterward; this is not a process-RSS or global-memory cap.

The separate single-result pending pool accepts at most:

- **536,870,912 bytes (512 MiB)** for the image's actual `bytesPerRow × height`, including row padding
- **134,217,728 bytes (128 MiB)** of known compressed/provider input, carried from the system decoder without copying provider contents
- Their sum, at most **671,088,640 bytes (640 MiB)**, for one pending capture

The panel displays the actual managed byte reservation and the separate ceilings. Pending bytes are included in subsequent editor admission and editable-history decoding allowance. An exact pending-ID plus image-identity handoff counts the image/encoded input once, while reserving the normal new-editor redraw cache. Known encoded input continues to count for that editor until it actually closes. Unrelated image opens cannot claim this transfer exemption.

Display/frozen/advanced captures retain the existing **64,000,000-pixel / 32,768-side** limits. Selected frozen crops already materialize detached 8-bit RGBA; recovery adds no crop clone. SCK explicitly requests BGRA and validates the returned storage layout before accepting it. Multi-window and scroll composites retain their existing smaller producer limits.

Apple's system selector previously used the generic `CGImage.read` path, which allowed 100 million pixels and 128 MiB compressed input but did not constrain component depth or decoded row storage. Its dedicated decoder preserves the **100,000,000-pixel** and **128 MiB file** limits. It now requires complete dimensions/depth metadata, rejects a 4/8-byte-per-pixel header estimate over 512 MiB, then checks an **uncached** ImageIO image's actual row stride/component layout before any caller draws/encodes it. Up to 16-bit components are supported if their storage fits; a 100M-pixel 8-bit image fits, while a 100M-pixel 16-bit RGBA image is explicitly refused before ImageIO image creation. The no-cache option does not prove ImageIO never decodes/allocates internally while creating an image; the actual stride check precedes application drawing, not a guaranteed system allocation boundary. Unsupported/malformed/oversized source formats are capture errors, not successfully acquired recoverable screenshots.

The 640 MiB number bounds the explicitly managed image raster reservation and known encoded input. It does **not** bound private ImageIO caches, SCK/GPU/WindowServer surfaces, allocator overhead, encoder transients, other windows or entire process RSS. A strict global 768 MiB ceiling plus lossless fallback is impossible with the current post-acquisition APIs if editor admission and disk both fail. The separate pending pool intentionally allows accepted capture pixels to survive that situation; it does not pretend that the old editor-only budget covers all app memory. Unexpected system-private allocations or an unsupported returned native layout cannot be covered by the managed-backing proof.

## File publication

Recovery streams PNG directly from the original image to a bounded `CGDataConsumer`; encoded output is limited to **640 MiB** without buffering a full encoded `Data`, constructing `ImageExportSnapshot`, or decoding a preview. One save runs for the one pending capture. Temporary output lives in a private sibling directory created/opened relative to the verified parent descriptor. The file is fsynced and published with an exclusive `linkat`, so an existing file is never overwritten, including after a save-panel Replace response. Cancellation shares the normal export commit fence: cancellation before publication keeps the result pending; a committed publication remains success even if cancellation arrives afterward. Stage files are removed in either outcome. Directory fsync is best effort, matching the existing save workflow; crash-proof storage hardware guarantees are not claimed. Capture date is kept in the pending/editor handoff and supplied to the PNG encoder as EXIF original-time metadata.

## Verification boundary

New XCTest coverage exercises the production completion coordinator with an actual `HistoryStore.beforeIndexCommit` failure, both count and budget refusal, unchanged CGImage identity/exact rendered pixels/date, replacement rejection, successful history/editor alternatives, stale completion, picker/save cancellation, failure, retry and explicit discard. Native AppKit target/action tests cover the actual compact controls, hidden/closed recovery UI, quit refusal, actual six-window rejection, pending-aware admission and no-double-count transfer, plus the actual entry point refusing a full editor count before acquisition or window hiding. An explicitly isolated application save workflow prevents fixture actions from reading normal automatic-save preferences or writing normal output destinations.

PNG tests exercise real streaming output, exact pixel readback, actual byte-limit/collision failures, an injected disk/commit failure, cancellation, exclusive publication and stage cleanup. System decoder tests cover invalid/oversized input, exact encoded-byte accounting, source-file deletion, surviving original pixels and provider/image release after recovery discard. Policy tests cover exact ceilings, depth/pixel/header rejection, overflow and pending accounting.

**Authored, not yet executed natively:** this editing environment has no Swift compiler or macOS/AppKit runtime. These tests and the changed app must compile and pass on macOS for the exact integrated source. Native system-selector/SCK capture with real permission/Retina/multi-display configurations, physical resource sampling, crash recovery and installed-package behavior are not established by synthetic tests. No native acceptance, installation, publication or release promotion is claimed by this patch.
