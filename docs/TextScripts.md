# Bounded local text scripting

Experimental ARM **0.22.0/build263** qualifies for the user-opted fixed route: one region capture → local OCR → an explicitly saved JavaScript text transformation → checked text Copy. The separate editor/catalog, shared action-chain owner, cached Copy retry and Close cleanup pass exact-source native and both actual ZIP/DMG checks in the [263 record](#build263-experimental-installed-qualification). The independently audited standalone runtime254 remains separate historical evidence. Stable214, retained Intel69, original227 memory failures and full PixPin/real-ScreenCaptureKit limitations remain unchanged.

## Language and process boundary

The implementation compiles an editable function body with the public JavaScriptCore C `JSObjectMakeFunction` API, passing recognized text as a separate string argument. It never interpolates input into source. A fresh noninspectable context has no native host objects, JSExport bridge, capture/clipboard/UI access, Node/JXA/browser APIs, file/network/process facilities or downloaded modules. Standard JavaScript language features remain available, including loops, allocation, regular expressions and nondeterministic Date/random values. This is not a small expression language or a deterministic-evaluation guarantee.

Only a primitive string can be returned. Objects, promises and boxed strings are rejected before coercion; exception values are never stringified. UTF-16 is inspected before allocating a native result, malformed surrogates are rejected, and accepted output preserves its characters without trimming. Errors use fixed codes, with no script/OCR/returned-text content in process metrics or stderr receipts.

The helper is a separate executable with its own `com.apple.security.app-sandbox=true` entitlement. It has no inheritance, network, user-file, automation or application-group entitlement. The parent remains unsandboxed. Apple documents this independent-child arrangement in [Resolving App Sandbox Inheritance Problems](https://developer.apple.com/forums/thread/706390); Build263 binds the exact ad hoc signatures, final/relocated helper identities and actual installed launches; this is experimental qualification, not stable acceptance. Final helper entitlements and signing identities are checked after the outer bundle is signed. There is no unsandboxed fallback, private JavaScriptCore timeout API, sandbox-exec profile or OS-permission acceptance.

The absence of host APIs limits what script code can request. App Sandbox adds OS access restrictions but permits its own container and some system resources; it is not a promise of zero filesystem access or protection against every engine/OS vulnerability. Code-signature validity on an ad hoc build does not establish a verified external publisher.

## Fixed runtime limits

- Source body: 16 KiB UTF-8
- Input and output: 32,768 UTF-16 units; output additionally 128 KiB UTF-8; empty results rejected
- Request: 512 KiB; response: 256 KiB with exact schema/UUID and one newline-terminated response
- One admitted helper; no queued image-bearing requests
- Three-second parent helper-phase acceptance deadline; 0.25-second termination grace, then 0.75-second killed-exit observation
- CPU soft/hard limits: two/three seconds; five-second independent helper alarm; core dumps and regular-file data growth disabled
- Child RSS watchdog: 256 MiB, sampled about every 50 ms; missing observation fails closed

The kernel limits are installed and read back before evaluating code. A sampled RSS watchdog is not a hard memory allocation cap and may overshoot between observations. File-size limits do not bound pipes or heap allocations. Alarm/deadline observations are not universal hard real-time completion guarantees. Deadline, cancellation or failed protocol results cannot be published even if output bytes arrived earlier.

The parent uses bounded nonblocking pipes and only count/EOF drainage for stderr. All pipe endpoints explicitly have close-on-exec set; intended standard descriptors are duplicated for the child. No request/output temporary file or ambient credentials/environment override is provided. A successful result requires validated protocol and observed child exit. Unconfirmed exit or pipes retain admission; after failure/cancellation retained response bytes are discarded while required descriptor/process ownership stays alive for later cleanup.

## Standalone native runtime experiment

The `[text-script-runtime]` job builds a dependency-free temporary SwiftPM package from an exact hash inventory of the new core/helper/client/fixture/test files. It checks a clean checkout and source commit, runs the isolated core/helper XCTest methods, and signs a standalone gate app. This does not rebuild or change the delivered PicShot product, codecs, models or disputed scroll-memory cell.

The normal path uses the actual helper with real pipes, generated Unicode/regex strings, strict diagnostics, absent-host-API checks, input/output bounds, cancellation, CPU/allocation pressure and a main-runloop heartbeat. Native-only probes attempt permission-denied read/write opens on parent-owned generated sentinels and a connection to a parent-owned loopback listener; the parent establishes positive baselines first. These are specific capability checks, not an exhaustive sandbox proof. They never expose a probe to JavaScript or read file contents into a report.

A distinct signed sandboxed **test-only** transport executable exercises malformed, oversized, wrong-identity, duplicate, unterminated, multiple and late responses, blocked termination and stderr flooding through the same parent wire code. It is explicitly injected only in the native gate build and is not a production fallback. A short-lived gate child separately launches the actual helper to verify its parent-loss alarm with owned PID/kqueue exit-status observation.

Reports retain exact source/signing identities, fixed outcomes, bounds, timings, probe errno values, heartbeat gaps and cleanup receipts. They contain generated-input evidence only. A sandbox-launch, identity or cleanup failure blocks this runtime approach until its concrete cause is resolved. No permission exception or resource-limit change is inferred from a failed run.

The standalone gate required later integration to preserve image-chain v1 bytes, use one existing capture/receipt owner, freeze saved script/OCR options per run, cache successful transformation for clipboard-only retry and reject truncated OCR without the direct OCR UI/automatic-copy route. Those checks are now recorded separately under263; standalone254 alone never established app delivery or full PixPin compatibility.

### First integrated product scope (pending native qualification)

The existing screenshot-action menu and manager open a compact text-script editor. New creates an unsaved issue-ID extraction example. Only explicit Save writes a definition; dirty selection/Close/Quit requires Save or Discard. Run uses a clean saved definition, starts unbound to global shortcuts, captures one region, recognizes text locally, evaluates the saved function body in the verified helper, and requires acknowledged text Copy. Scripts receive `text` only; they cannot call PicShot actions or access capture, files, network, processes or clipboard APIs. There is no file import, downloaded script, shared-library loading or arbitrary action graph in this slice.

`text-scripts.json` is separate from the existing image-chain catalog: schema1, at most32 definitions, 16 KiB source per definition and 1 MiB total encoded file. Strict decoding rejects unknown fields, duplicate keys/IDs, unsupported versions and oversized/corrupt data. Only names, IDs, deliberately saved source and selection are persisted. Unsaved drafts, recognized/returned text, images, exception objects and run receipts have no catalog fields. Save and selection are atomic together; failed writes retain previous disk and in-memory values. This is bounded local persistence, not multi-process conflict resolution.

Both image and text routes reserve the same active runner before acquisition. OCR failure retries the same capture; transformation failure retries frozen recognized text/source; rejected Copy retries the cached transformed string without new acquisition, OCR or evaluation. Successful earlier phases can release their superseded payloads. Terminal status retains only metadata and counts. An acknowledged Copy receipt is inserted synchronously before any subsequent cancellation check. Cancel/Close clears sensitive buffers and continues owning unresolved helper cleanup; new capture/Quit remain blocked until that owned exit and pipe drainage are observed. Fixed diagnostics never retain arbitrary thrown text.

The shared progress surface still requires the legacy image-action catalog to load. If that catalog is corrupt/unavailable, starting a text action fails before acquisition or helper execution and surfaces fixed feedback; it does not overwrite the legacy file or reconstruct a catalog. The initial script editor has no portable-settings export or global binding. A failed recipient write cannot restore prior clipboard contents after the clear operation; the transformed result remains available for retry while the run is open.

Production packaging installs the exact helper with its sole sandbox entitlement after the established nested signing pass, then re-seals only the outer app. Source-bound verification requires final and relocated signature/plist identity. Native integration additionally needs actual Vision OCR of generated content, the production helper and a private pasteboard, with an injected first Copy refusal, unchanged image-chain behavior, real light/dark control geometry and bounded ownership release. Packaging proof alone is not those runtime assertions. Original227 memory failures and all experimental/real-SCK limitations remain active; no stable ledger promotion follows from this candidate.
